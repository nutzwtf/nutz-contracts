## R03 — Theft property: tokens only reach the leaf's `account` (two named exceptions), and arrive or are recorded in `stuck`

> "No function callable by an arbitrary address moves tokens to anyone but `account` in a valid leaf (the push fee to the Keeper and `pullAcorn` to the Converter are the two named exceptions), and every allowed amount either arrived or is recorded in `stuck`."
> — docs/spec/engineering-spec.md §7 (L322)

Supporting text, same document:

> "`claim(kind, id, account, amounts[5], proof)` — permissionless; tokens always go to `account`. […] a failing token lands in `stuck[account][token]`, never blocking the others."
> — §3.3 (L167)

> "`pushClaims(PushEntry[], gasPriceWei, usdgPerEth)` — `onlyKeeper`. […] Stocks in full, USDG minus fee to the holder, the batch's total fee in one transfer to `msg.sender` (the gas payer)."
> — §3.3 (L168)

**Verdict:** implemented · confidence: high

**What this demands of an implementation:** enumerate every instruction in `src/NutzDistributor.sol` that moves a token out of the contract and show that (1) its destination is the `account` bound into a Merkle leaf that verified against a posted Root, or (2) it is the push fee going to the Keeper on a Keeper-only path, or (3) it is `pullAcorn` sending USDG to `CONVERTER`; and that for (1) the amount is either transferred or added to `stuck[account][token]`.

Arrival-or-stuck:

```solidity
// src/NutzDistributor.sol:L469-L488
    function _payout(address account, uint256[5] memory amounts) private {
        for (uint256 i = 0; i < 5; i++) {
            uint256 amount = amounts[i];
            if (amount == 0) continue;
            if (!_tryTransfer(tokens(i), account, amount)) {
                stuckOf[account][i] += amount;
                emit Stuck(account, i, amount);
            }
        }
    }
    function _tryTransfer(IERC20 token, address to, uint256 amount) private returns (bool) {
        (bool ok, bytes memory ret) = address(token).call(abi.encodeCall(IERC20.transfer, (to, amount)));
        return ok && (ret.length == 0 || abi.decode(ret, (bool)));
    }
```
- A revert (`ok == false`) or a `false` return records the full amount in `stuckOf[account][i]`; a success is the arrival. `claimStuck` (L433-439) zeroes the record before a `safeTransfer` that reverts on failure, so the record is restored by the revert and the amount is never dropped.

**Paths walked:**
- `claim` (arbitrary caller) → `_settle(…, account, …)` → `_payout(account, amounts)`. Destination = leaf account. ✓
- `claimMany` (arbitrary caller) → all leaves settled for the one `account` argument (L366) → `_payout(account, sum)`. ✓
- `pushClaims` → `onlyKeeper` (L387; `Signers.sol` L52-55 compares `msg.sender` to `keeper`): not callable by an arbitrary address. Its two destinations are `pe.account` (the settled leaf's account) and `msg.sender == keeper` (the named fee exception). The fee is deducted from USDG only (L406) and bounded by R04. ✓
- `claimStuck` (arbitrary caller) → pays `account` from `stuckOf[account][t]`, which only `_payout` credits (L474) and only to its own `account` parameter. So the destination is again a leaf account or the Keeper's stuck fee. ✓
- `pullAcorn` → `onlyConverter` (L223), pays `msg.sender == CONVERTER` (L233) the whole `acornPoolUsdg`, which only `notifyEpochFunding` credits (L212). Named exception. ✓
- `notifyEpochFunding`, `notifyDrawFunding` → inbound only, `onlyConverter`. ✓
- Governance (`setRateRange` L423, `proposeDrawContract` L493, `executeDrawContract` L500, `proposeExclusion` L508, `executeExclusion` L515) and `Signers` (`setKeeper`, `proposeSignerRotation`, `executeSignerRotation`, `cancel`, `Signers.sol` L58-89): no token instruction on any of them.
- ETH: no `receive`, `fallback` or `payable` in src/NutzDistributor.sol (grep `payable|receive\(|fallback` → 0 hits in that file). The contract cannot hold or move ETH.
- Re-entrancy from a token callback into a second payout: every external entry point that pays is `nonReentrant` (L347, L360, L386, L433); `_settle` marks `B.claimed[id][account]` (L455) before any transfer, so a replay of the same leaf reverts `AlreadyClaimed`.

**How the verdict was reached:** the file has exactly two outbound transfer primitives (`_tryTransfer` via `_payout`, and `safeTransfer` in `pullAcorn`/`claimStuck`); each caller's destination variable is either the leaf-bound `account` or a role-gated `msg.sender` that the requirement names. The arrival-or-stuck clause is a two-branch function with no third outcome except a full revert. Not `partial`: no outbound path was found outside the table.

**Open questions:**
- `_tryTransfer` L487: if a token returns data that is neither empty nor a well-formed 32-byte bool (for example 1..31 bytes, or a word other than 0/1), `abi.decode(ret, (bool))` reverts, so the whole claim reverts instead of recording `stuck`. The allocation stays unclaimed (state is rolled back), so nothing is lost or misdirected, but that token would block the other four for that claim until it behaves. The five reward tokens are fixed immutables; whether any of them can ever return such data is a token-behaviour question, not something this file establishes. Recording for the reviewer; it does not change the verdict.
- A reward token address with no code would make `call` succeed with empty return and count as "arrived". The five immutables are checked non-zero (L177) but not for code size. On the target chain they are live contracts; noted only because "arrived" in that case is the contract's belief, not a fact it verified.
