## R06 — No admin backdoors: no owner, no upgrade proxy, no pause on claims, no token rescue for reward tokens

> "**No admin backdoors:** no owner, no upgrade proxy, no pause on claims, no token rescue for reward tokens. This must be visible in the verified source — it is a marketing feature."
> — docs/spec/engineering-spec.md §6 (L285)

Supporting text, same document:

> "- **No owner. No pause. No withdraw. Never holds ETH.**"
> — §3.2 (L160)

> "It never holds Reward Tokens between calls, has no owner, no withdraw, no pause, no upgrade and no way to change the Pons fee recipient."
> — §2 (L39)

> "`NutzDraw` holds no funds and has no governance"
> — §3.4 (L179)

**Verdict:** implemented · confidence: high

**What this demands of an implementation:** across `src/NutzDistributor.sol`, `src/NutzConverter.sol`, `src/NutzDraw.sol`, `src/Signers.sol` (and the bases they inherit): no single-key owner role; no proxy pattern, `delegatecall`, initializer, or `selfdestruct` that could replace logic; no state that any role can set to make `claim`/`claimMany`/`claimStuck` revert; and no function that transfers a reward token (SPY, NVDA, MU, SPCX, USDG) to a role-chosen address. This is an absence claim across four files, so the searches are the evidence.

**Where enforcement lives:** enforcement here is the absence of code plus the shape of what exists.

`_settle` (L446-463) reads `isFinal`, `B.claimed`, `L.root`, `L.totals`; none is writable by a role once the Root is Final (`voidRoot` needs `!isFinal`, L310; nothing else writes them).

Every outbound reward-token move, per contract:
- Distributor: `_payout` → leaf `account` or Keeper fee (L350, L371, L412, L417); `claimStuck` → the stuck record's `account` (L438); `pullAcorn` → `CONVERTER` (L233). All walked in R03; no destination is chosen by a role.
- Converter: reward tokens leave only to a Venue as swap input (`_runV3` L612-613 under an exact approval; `unlockCallback` L690 to the pool manager) and to the Distributor under exact approvals (`_approveFunding` L504-509, `_fundEpoch` L493-498, `_fundDraw` L547-551). No function takes a recipient address for a token. Stray reward tokens sent to the Converter have no exit at all (the stock legs spend `perStock` computed from the swap output, L335-341, not the balance) — consistent with "no token rescue" and §2.2 "nothing else has an exit".
- Draw: no token instruction in the file (grep below).

`unlockCallback` (Converter L656-697) looks like an open hand into the contract's balances but is only reachable as the callback of the Converter's own `unlock` call: lib/v4-core/src/PoolManager.sol L109 `IUnlockCallback(msg.sender).unlockCallback(data)` calls back the *caller of `unlock`*, and L657 additionally requires `msg.sender == V4_POOL_MANAGER`. An arbitrary address calling `unlock` gets its own callback, not the Converter's.

**Paths walked:**
- Roles that exist and what they can do: Signers 2-of-3 (`postRoot`, `voidRoot`, `setRateRange`, `setKeeper`, `setOpsCap`, `disableLeg`, timelocked `proposeSignerRotation`/`proposeDrawContract`/`proposeExclusion`/`proposeLegEnable`, `cancel`); Keeper (`pushClaims`, `sweep`, `convertAcorn`, `bindNutz`, `requestDraw`). None of these sets a flag that `claim*` reads, replaces code, or names a token recipient. ✓
- The closest thing to a role-directed value flow: `_fundOps` (Converter L433-443) sends ETH to `keeper`, and Signers set both `keeper` (Signers.sol L58-63, instant) and `opsCap` (L262-267, instant). It is bounded to 2% of each Sweep (L436) and to topping the Keeper up to `opsCap ≤ MAX_OPS_CAP_WEI = 5 ether` (L86, L221, L263), it is ETH not a reward token, and it is the §2.2 step 3 Ops Slice the document specifies. Not a backdoor under this requirement; recorded because it is the one place Signers direct value.
- `executeDrawContract` (Distributor L500-505) lets Signers, after 48h, point `drawContract` at any address. That contract only answers `seedOf` (L253), which gates `pullAcorn` and Draw Roots; it cannot redirect tokens (destinations are unchanged, R03). Disclosed in §3.4. ✓
- `Signers.executeSignerRotation` (L74-80) can rotate keys after 48h but only under a 2-of-3 proposal; there is no single-key path anywhere (`_require2of3` L121-129 needs two distinct Signer addresses). ✓
- `receive()` in the Converter (L240) accepts ETH and does nothing; the Distributor and Draw have no `receive`/`fallback`/`payable`. ✓

**How the verdict was reached:** four vocabularies for owner/pause/upgrade/rescue each returned only comments; the inheritance chains are known non-privileged bases; every claim entry point has no gate a role can flip; and every reward-token outflow has a destination fixed by a Merkle leaf, the immutable `CONVERTER`, the Distributor, or a swap Venue. That is what "visible in the verified source" can mean, and it is visible. Not `partial`: no role-controlled path to claims or reward tokens was found in any of the four files.

**Open questions:**
- None for this requirement. The Ops Slice and the Draw-contract replacement are role-directed but are what the document specifies; if the reviewer wants them called out under "no admin backdoors" in the published copy, that is a documentation choice, not a code gap.
