## R12 — Reentrancy / accounting: `nonReentrant` on all external state-changing functions, CEI, SafeERC20

> "**Threat: reentrancy / accounting.** `nonReentrant` on all external state-changing functions; checks-effects-interactions; SafeERC20."
> — docs/spec/engineering-spec.md §6

> "`receive()` — accepts ETH from anyone: the Pons escrow on `claim()`, the curve on an owner-only `rescueCurveFees` (which bypasses the escrow), refunds, donations. It never reverts and does nothing but accept."
> — docs/spec/engineering-spec.md §2.2

> "`unlockCallback(bytes)` — the v4 pool manager's callback (`NotPoolManager` for anyone else)"
> — docs/spec/engineering-spec.md §2.2

**Verdict:** partial · confidence: high

The reentrancy *property* holds on every entry point of both contracts (every external state-changing function that makes an external call is guarded, or is only reachable while the guard is already held). The document's *mechanism* claim — "`nonReentrant` on all external state-changing functions" — is not what the code does: sixteen external state-changing functions carry no guard, and for two of them (`receive`, `unlockCallback`) adding it would break the Sweep. No behavioural consequence; the fix belongs in the document.

**What this demands of an implementation:** (1) every `external`/`public` non-view function that writes storage carries OZ `nonReentrant`; (2) within each such function, storage writes precede external calls; (3) ERC-20 interactions go through `SafeERC20`.

**What a re-entrant caller can reach mid-Sweep** (a hostile v4 hook, a Venue, or a Reward Token proxy): `sweep`/`convertAcorn` → guard revert; `unlockCallback` → `NotPoolManager` unless via the manager, and the manager rejects a nested `unlock` (`AlreadyUnlocked`, PoolManager L104); Distributor's guarded functions from inside `notifyEpochFunding` → guard revert; Distributor's `claim` from inside a *Venue* call (Distributor guard not held then) → allowed, but it changes only claim ledgers, which `notifyEpochFunding` does not read; the permissionless `execute*` functions (no guard) → allowed, but each only performs an action already ready for anyone, e.g. `executeLegEnable` mid-Sweep flips `legDisabled[stock]` between two stock Legs, with the same outcome as executing it one block earlier; `receive` → accepts ETH after `ethIn` was fixed at L327, no effect on the running call.

**SafeERC20:**
- Converter: `forceApprove` L506, L508, L612, L619; `safeTransfer` L690 (`using SafeERC20 for IERC20`, L34). `IERC20(nutz).balanceOf` (L416) and `T4.balanceOf` (L529, L531) are views. ✓
- Distributor: `safeTransferFrom` L215, L218, L246; `safeTransfer` L233, L438 (`using`, L17). ✓
- Distributor `_tryTransfer` L485-L488 is a raw `.call(abi.encodeCall(IERC20.transfer, …))` by design ("reports failure instead of reverting", L480-L481). It treats `ok && returndata empty` as success *without* a code-size check, whereas OZ's `_safeTransfer` (SafeERC20 v5.7.0 L188-L209) additionally requires `extcodesize(token) > 0` on the empty-return branch. A token address with no code would therefore be paid "successfully" and the amount marked claimed. The five tokens are immutables checked non-zero (L175-L178) but not checked for code; they are proxies on the live chain. Documented deviation from "SafeERC20"; no reachable consequence with the deployed tokens. —

**How the verdict was reached:** `partial` rather than `implemented` because the document states a universal mechanism ("all external state-changing functions") and the code applies it to eleven of twenty-seven such functions; `partial` rather than `contradicted` because every unguarded function either makes no external call at all or is only reachable while a guard is already held, so the threat the sentence addresses is closed on every path walked. The two functions where the modifier is impossible (`receive`, `unlockCallback`) are the reason the sentence cannot be made literally true. Severity per the rubric: documentation drift, Low.

**Open questions:**
- Document: restate as "`nonReentrant` on every external function that makes an external call; `receive` and `unlockCallback` are guarded by the calling Sweep's guard and the pool manager's own lock", or equivalent.
- `_tryTransfer`'s missing code-size check versus the "SafeERC20" claim: harmless with the deployed proxies; a constructor `code.length > 0` check on the five tokens would close it for good.
- The `stuckOf` write after a failed transfer in `_payout` is CEI-by-necessity under the guard; no action needed unless views are expected to be consistent mid-call.
