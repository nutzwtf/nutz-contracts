## R05 — `voidRoot` only inside the 30 min Dispute window; afterwards Final and claimable; void restores Carry exactly and keeps funding

> "30 min dispute window in which anyone can run `nutz-verify`; […] `voidRoot` for the window."
> — docs/spec/engineering-spec.md §6, "Threat: bad root" (L269)

The void semantics are stated in §3.3, not §2 (the brief's pointer; §2 is the Converter and has no void text):

> "`voidRoot(kind, id, sig1, sig2)` — 2-of-3, only the **latest** Root of that Kind, only before Final. Restores Carry exactly (`carry + totals − funded`), clears the Root, keeps the period's funding, moves the mark back by one: a corrected Root for the **same** period is posted next ("one period, one tree"). To void an earlier Root, void the later ones first."
> — §3.3 (L165)

> "**Dispute window:** claims revert until `rootPostedAt + CLAIM_DELAY`; after that the Root is Final and cannot be voided."
> — §3.3 (L166)

> "Constants: `CLAIM_DELAY = 30 min`, `MAX_PUSH_FEE_BPS = 500`. "Final" is a view (`isFinal`): Root posted and the Dispute window elapsed."
> — §3.1 (L154)

Also docs/adr/0002-ordered-roots-carry-in-full.md L8: "`voidRoot` is allowed only on the latest Root and before it is Final: it restores Carry exactly, clears the Root and moves the mark back by one"; and L21: "Void restores Carry with `carry + totals − funded`, which is exact only because no later Root can exist at that point."

**Verdict:** implemented · confidence: high

**What this demands of an implementation:** (a) a Root can be voided only while `block.timestamp < rootPostedAt + 30 minutes`; (b) once that instant passes the Root cannot be voided and its leaves can be claimed; (c) the void must set the Book's Carry back to exactly what it was before the Root was posted, for every token; (d) the period's `funded` must be left in place; (e) the mark must move back so the same period is the next to be rooted.

**Where enforcement lives:**

```solidity
// src/NutzDistributor.sol:L42
    uint256 public constant CLAIM_DELAY = 30 minutes;
// src/NutzDistributor.sol:L577-L581
    function isFinal(Kind kind, uint256 id) public view returns (bool) {
        uint256 postedAt = _book(kind).ledgers[id].rootPostedAt;
        return postedAt != 0 && block.timestamp >= postedAt + CLAIM_DELAY;
    }
// src/NutzDistributor.sol:L306-L323
    function voidRoot(Kind kind, uint256 id, bytes calldata sig1, bytes calldata sig2) external nonReentrant {
        Book storage B = _book(kind);
        Ledger storage L = B.ledgers[id];
        if (L.rootPostedAt == 0) revert NoRoot(id);
        if (isFinal(kind, id)) revert RootIsFinal(id);
        if (id != B.rootedThrough) revert NotLatestRoot(id);
        _require2of3(keccak256(abi.encode(VOID_ROOT_TYPEHASH, uint8(kind), id, nonce)), sig1, sig2);

        for (uint256 i = 0; i < 5; i++) {
            B.carry[i] = B.carry[i] + L.totals[i] - L.funded[i];
        }
        delete L.root;
        delete L.totals;
        delete L.rootPostedAt;
        B.rootedThrough = id - 1;
        emit RootVoided(kind, id);
    }
// src/NutzDistributor.sol:L449   the claim side of the same boundary
        if (!isFinal(kind, id)) revert NotFinal(id);
```
- (a) L310 with L580: void is refused from `postedAt + 30 min` onward. (b) L449 admits claims from the same instant; the boundary uses `>=` on both sides, so there is no timestamp at which both void and claim are possible, and none at which neither is.
- (c) L315-317: `postRoot` set `carry = funded + carryIn − totals` (L291-294, R01), so `carry + totals − funded == carryIn`. Exactness depends on nothing touching `B.carry`, `L.totals` or `L.funded` in between — walked below. No underflow: `carry + totals = funded + carryIn ≥ funded`.
- (d) `L.funded` is not written (L318-320 delete only `root`, `totals`, `rootPostedAt`).
- (e) L321 `rootedThrough = id − 1`; `postRoot` then requires `id > rootedThrough` (L272) and its skip loop `for x = id; x < id` (L284) is empty, so the next Root for `id` sees `carryIn == carry` restored.

**Paths walked:**
- Void inside the window, latest Root → all guards pass → Carry restored, Root cleared. ✓
- Void at or after `postedAt + 30 min` → L310 `RootIsFinal`. ✓ Claim before that instant → L449 `NotFinal`. ✓
- Between post and void, what can change the three quantities? `B.carry`: `postRoot` L294 and `_skip` L332 (only inside `postRoot`), but any later `postRoot` moves `rootedThrough` past `id`, after which L311 refuses the void; `voidRoot` itself. `L.totals`: L297 and L319 only. `L.funded`: `notifyEpochFunding` L207 / `notifyDrawFunding` L239 refuse `id <= rootedThrough`, and `rootedThrough == id` while the Root stands. So none of the three can change while the void is still permitted; the restoration is exact. ✓
- Void of an earlier Root while a later one stands → L311 `NotLatestRoot`; after voiding the later one, `rootedThrough == id − 1` and the earlier Root (if still inside its own window) passes L309-311. Matches "void the later ones first". ✓
- Skipped periods between the old mark and `id`: their funding entered Carry during `postRoot` before `carryIn` was snapshotted (L284-289), and the void restores Carry to that snapshot, so the skipped funding remains in Carry and the skipped ledgers (now `<= rootedThrough`) stay closed. Consistent with §3.3. ✓
- Period funded again after a void (allowed: `id > id − 1`) and re-posted: cap computed on the new `funded` plus restored Carry. ✓
- `_require2of3` L312 is evaluated after the state guards, so a signed void of a Final Root does not consume the nonce. (Ordering note only.)

**Searched:**
- `rootPostedAt` in src/NutzDistributor.sol → L30 field, L298 set, L309 guard, L320 delete, L578 read. No other writer: `isFinal`, once true, stays true unless voided, and void needs `!isFinal`.
- `CLAIM_DELAY` → L42, L580 only.
- `isFinal` callers → L310 (`voidRoot`), L449 (`_settle`). No claim path bypasses it (`_settle` callers: L349, L366, L399).
- `rootedThrough` writers → L193-194 (constructor), L299 (`postRoot`), L321 (`voidRoot`).

**How the verdict was reached:** the window is one constant and one comparison used by both the void guard and the claim guard; the Carry arithmetic is the algebraic inverse of `postRoot`'s and the three inputs are provably frozen while the void is permitted. The "latest only" and "keeps funding" clauses are explicit in §3.3 and ADR-0002, so this is `implemented`, not `stronger-than-spec`.
