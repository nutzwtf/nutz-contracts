## R01 — Per-Root cap `totals ≤ funded + carryIn`, remainder becomes Carry

> "Per Root: `totals[t] ≤ funded[t] + carryIn[t]` for all t, enforced at `postRoot`; the remainder is the next Carry."
> — docs/spec/engineering-spec.md §7 (L319)

Supporting text, same document:

> "Then `totals[i] <= funded[i] + carry[i]`, `carry[i] = funded[i] + carry[i] − totals[i]`. Emits `RootPosted(kind, id, root, totals, carryIn)` so the verifier can reproduce the cap."
> — §3.3 (L164)

**Verdict:** implemented · confidence: high

**What this demands of an implementation:** in `postRoot`, for every token index t in 0..4, the posted `totals[t]` must be compared against `ledgers[id].funded[t] + carry[t]` (the Carry as it stands when the Root is posted, after any Skips of the same call) and rejected if larger; and the Book's `carry[t]` must be set to exactly `funded[t] + carryIn[t] − totals[t]`. Nothing else may write `totals`, and `funded` of a rooted period must not change afterwards, or the cap would be enforced against a stale quantity.

**Where enforcement lives:**

```solidity
// src/NutzDistributor.sol:L284-L300
        for (uint256 x = B.rootedThrough + 1; x < id; x++) {
            _skip(kind, B, x);
        }

        Ledger storage L = B.ledgers[id];
        uint256[5] memory carryIn = B.carry;
        for (uint256 i = 0; i < 5; i++) {
            uint256 available = L.funded[i] + carryIn[i];
            // forge-lint: disable-next-line(require-revert-in-loop)
            if (totals[i] > available) revert CapExceeded(i);
            B.carry[i] = available - totals[i];
        }
        L.root = root;
        L.totals = totals;
        L.rootPostedAt = block.timestamp;
        B.rootedThrough = id;
        emit RootPosted(kind, id, root, totals, carryIn);
```
- L289 snapshots `carryIn` after the Skip loop (L284-286), so the Carry compared against already includes the funding of every period passed over in this call, which is what §3.3 says ("its funding rolls into Carry in the same call").
- L291-294: all five indices are checked; a violation reverts the whole call (`CapExceeded(i)`), so no partial state. `available − totals[i]` cannot underflow because the check on L293 precedes it. `L.funded[i] + carryIn[i]` is checked arithmetic (Solidity 0.8.37, L2), so an overflow reverts rather than wrapping the cap.
- L297: `totals` is stored only here. The only other write is `delete L.totals` in `voidRoot` (L319).
- `_skip` (L325-339) adds a passed-over period's `funded` to `B.carry` and marks it `skipped`; it never touches `totals`.

**Paths walked:**
- `postRoot(Kind.Epoch, …)` → order checks L272-273 → 2-of-3 L278 → skips → cap loop L290-295. ✓
- `postRoot(Kind.Draw, …)` → same code; extra gates L274-277 (`drawConverted`, seed) precede the same cap loop. ✓
- Can `funded[id]` grow after the Root is posted, making the enforced cap stale? `notifyEpochFunding` L207 reverts `PeriodClosed` when `epochId <= epochBook.rootedThrough`, and `postRoot` sets `rootedThrough = id` (L299), so no. `notifyDrawFunding` L239 has the same gate against `drawBook.rootedThrough`. ✓
- After `voidRoot` (L306-323) the mark moves to `id − 1` (L321) and `funded` is kept, so the period may be funded again and re-posted; the re-post runs the cap loop against the new `funded` and the restored Carry. ✓
- Is any other function able to write `B.carry`? `_skip` (L332, only from `postRoot`), `postRoot` L294, `voidRoot` L316. Nothing else (grep `carry` in src/NutzDistributor.sol: declaration L81, view L567-569, and those three writers).

**How the verdict was reached:** the comparison and the remainder assignment are both on the page, per token, on the only path that stores a Root, and the two quantities compared cannot drift after the Root is stored. Not `stronger-than-spec`: the ordering and Skip behaviour that surround the cap are themselves in §3.3 and ADR-0002.
