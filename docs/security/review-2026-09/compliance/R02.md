## R02 — Per rooted period `claimed[e][t] ≤ totals[e][t]`, over-allocating Roots stop at their totals

> "Per rooted period: `claimed[e][t] ≤ totals[e][t]` for all t, whatever the leaves sum to. A Root whose leaves over-allocate is accepted and stops paying at its totals, so a bad Root can misdirect at most one period (§6)."
> — docs/spec/engineering-spec.md §7 (L320)

Supporting text, same document:

> "`claim(kind, id, account, amounts[5], proof)` — permissionless; tokens always go to `account`. Checks Final, unclaimed, proof, `claimed[i] + amounts[i] <= totals[i]`; marks claimed; then transfers with per-token try/catch"
> — §3.3 (L167)

**Verdict:** implemented · confidence: high

**What this demands of an implementation:** (a) `postRoot` must not reject a Root on the basis of what its leaves sum to (it cannot see them; it must only cap `totals`, R01); (b) every path that settles a leaf must add the leaf's `amounts[t]` to the period's running `claimed[t]` and refuse when the sum would exceed the period's stored `totals[t]`, for each t; (c) no path may pay an amount that did not pass that check.

**Where enforcement lives:**

```solidity
// src/NutzDistributor.sol:L446-L463
    function _settle(Kind kind, uint256 id, address account, uint256[5] calldata amounts, bytes32[] calldata proof)
        private
    {
        if (!isFinal(kind, id)) revert NotFinal(id);
        Book storage B = _book(kind);
        if (B.claimed[id][account]) revert AlreadyClaimed(id, account);
        Ledger storage L = B.ledgers[id];
        bytes32 leaf = keccak256(bytes.concat(keccak256(abi.encode(id, account, amounts))));
        if (!MerkleProof.verifyCalldata(proof, L.root, leaf)) revert InvalidProof();
        B.claimed[id][account] = true;
        for (uint256 i = 0; i < 5; i++) {
            uint256 c = L.claimed[i] + amounts[i];
            // forge-lint: disable-next-line(require-revert-in-loop)
            if (c > L.totals[i]) revert CapExceeded(i);
            L.claimed[i] = c;
        }
        emit Claimed(kind, id, account, amounts);
    }
```
- L456-461: per token, the running `claimed` plus this leaf is compared to the stored `totals`; exceeding reverts the whole transaction (so a leaf that no longer fits is simply unpayable; earlier leaves were paid — "stops paying at its totals").
- `postRoot` L263-301 stores `root` (L296) without any leaf inspection: an over-allocating tree is accepted.
- `L.claimed` is written only at L460 (grep below); `L.totals` only at L297 and deleted at L319.

**Paths walked:**
- `claim` L345-351 → `_settle` → `_payout(account, amounts)` with the same `amounts` that passed the check. ✓
- `claimMany` L354-372 → `_settle` per id (L366), then `_payout(account, sum)` where `sum` is the elementwise sum of the settled leaves (L367-369). ✓ Any leaf failing reverts all (no partial settle survives).
- `pushClaims` L384-419 → `_settle` per leaf (L399), then `_payout(entries[n].account, sums[n])` with `sums[n] ≤` the settled sum (USDG reduced by the fee, L406) and `_payout(msg.sender, feeOnly)` where `totalFee = Σ fee_n ≤ Σ sum_n[USDG]` (L405-407). Total paid out per period never exceeds what `_settle` admitted. ✓
- `claimStuck` L433-439 pays `stuckOf[account][t]`, credited only in `_payout` L474 from amounts that passed `_settle`. ✓
- `voidRoot` L318-320 deletes `root`, `totals`, `rootPostedAt` but not `L.claimed`. Could a stale `claimed` leak into a re-posted Root? No: `_settle` requires `isFinal` (L449) and `voidRoot` requires `!isFinal` (L310); `isFinal` (L577-581) is monotone once true because only `voidRoot` clears `rootPostedAt`. So at the moment of a void no leaf of that period has ever been settled and `L.claimed` is all zero. ✓

The leaf is double-hashed (L453), matching OZ StandardMerkleTree; an interior node cannot be presented as a leaf because the leaf preimage is 32 bytes and interior preimages are 64.

**How the verdict was reached:** the per-token comparison is on the one settle path shared by all three claim entry points, every payout is derived from settled amounts, and the one place the period state is partially reset (`voidRoot`) is unreachable once any claim has happened. Not `partial`: no claim path bypasses `_settle`.
