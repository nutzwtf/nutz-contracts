## R17 — Distributor token balance ≥ Σ (funded − claimed) for every token, by construction

> "Distributor token balance ≥ `Σ (funded − claimed)` for all t."
> — engineering-spec.md §7, Invariants

> "Per Root: `totals[t] ≤ funded[t] + carryIn[t]` for all t, enforced at `postRoot`; the remainder is the next Carry. Globally: `Σ claimed[t] ≤ Σ funded[t]` for all t, always (Carry is earlier funding rolled forward, so it is already inside Σ funded)."
> — engineering-spec.md §7

> "`notifyEpochFunding(epochId, amounts[5], acornUsdg)` — `onlyConverter`. […] Adds to `funded` (several sweeps may fund one epoch) and `acornPoolUsdg`; pulls `amounts` plus `acornUsdg` of USDG."
> — engineering-spec.md §3.3

> "`claimStuck(account, token)` retries." / "the batch's total fee in one transfer to `msg.sender` (the gas payer)"
> — engineering-spec.md §3.3

**Verdict:** implemented · confidence: high

**What this demands of an implementation:** for each token `t`, let `F_t = Σ_periods funded[t]` over both books and `C_t = Σ_periods claimed[t]`. Every increment of `funded` must be matched by tokens arriving in the same transaction; every token leaving must be matched by an equal increment of `claimed` (or come from a pool that is not inside `F − C`, such as `acornPoolUsdg`); and `C_t ≤ F_t` must hold so the right-hand side never exceeds what arrived. Then `balance_t = F_t − C_t + stuck_t + acornPool_t + donations ≥ F_t − C_t`.

**Where enforcement lives:**

Inflows — state and tokens move together, or neither does:
```solidity
// NutzDistributor.sol:L209-L218 (notifyEpochFunding)
for (i < 5) L.funded[i] += amounts[i];
acornPoolUsdg += acornUsdg;
for (i < 4) if (amounts[i] > 0) tokens(i).safeTransferFrom(msg.sender, address(this), amounts[i]);
uint256 usdg = amounts[USDG] + acornUsdg;
if (usdg > 0) T4.safeTransferFrom(msg.sender, address(this), usdg);
```
```solidity
// NutzDistributor.sol:L241-L247 (notifyDrawFunding)
for (i < 5) L.funded[i] += amounts[i];
for (i < 5) if (amounts[i] > 0) tokens(i).safeTransferFrom(msg.sender, address(this), amounts[i]);
```
- `safeTransferFrom` (OZ `SafeERC20.sol:L44-L48`) reverts `SafeERC20FailedOperation` on a false return, and bubbles a revert (`_safeTransferFrom` with `bubble = true`, same pattern as `_safeTransfer` L200-L204), so a funding call that does not deliver the tokens undoes the `funded` increment. `acornUsdg` is pulled (L217-L218) but recorded in `acornPoolUsdg`, not `funded` — it sits above the invariant's right-hand side.

Cap chain — `C_t ≤ F_t`:
```solidity
// NutzDistributor.sol:L290-L295 (postRoot)
uint256 available = L.funded[i] + carryIn[i];
if (totals[i] > available) revert CapExceeded(i);
B.carry[i] = available - totals[i];
```
```solidity
// NutzDistributor.sol:L456-L461 (_settle)
uint256 c = L.claimed[i] + amounts[i];
if (c > L.totals[i]) revert CapExceeded(i);
L.claimed[i] = c;
```
- Invariant on `carry`: `carry = Σ funded(processed periods) − Σ totals(rooted periods)`. Established by: `_skip` L325-L339 adds a passed-over period's `funded` to `carry`; `postRoot` L294 sets `carry = funded[id] + carry − totals[id]` (non-negative by L293); `voidRoot` L315-L317 sets `carry = carry + totals − funded`, exact because (a) only the latest Root can be voided (L311) and (b) no funding can land on a period `≤ rootedThrough` (L207, L239), so nothing changed `carry` since that Root. After a void `rootedThrough = id − 1` (L321) and previously skipped periods `< id` are not re-walked (the skip loop L284 starts at `rootedThrough + 1 = id`), so their `funded` is not added to `carry` twice. Hence `Σ totals(rooted) ≤ Σ funded(processed) ≤ F_t`, and by L459 `C_t ≤ Σ totals(rooted)`.

Outflows — each matched to `claimed` or to the pool:
```solidity
// NutzDistributor.sol:L469-L488 (_payout / _tryTransfer)
if (!_tryTransfer(tokens(i), account, amount)) { stuckOf[account][i] += amount; emit Stuck(...); }
```
- `claim` L345-L351, `claimMany` L354-L372, `pushClaims` L384-L419: every `_payout` amount was first added to `L.claimed` in `_settle` (L399-L403 sum exactly the settled leaves; L364-L370 same). In `pushClaims` the holder's USDG is reduced by `fee` (L406) and the summed fees go to `msg.sender` (L414-L418): total USDG leaving = Σ settled USDG exactly, so the fee is inside `claimed`, not on top of it. `fee ≤ sum[USDG] × 500 / 10_000` (L405) so L406 cannot underflow.
- A failed transfer records `stuck` and keeps the tokens (L473-L476); `claimed` was already incremented, so `balance − (F − C)` rose by `amount` while `stuck` rose by `amount`. `claimStuck` L433-L439 then sends exactly the recorded amount and zeroes it (`safeTransfer`, reverting and restoring the record on failure).
- `pullAcorn` L228-L233 sends `acornPoolUsdg` and zeroes it; that USDG was never in `funded`. The Converter returns it as `funded` through `notifyDrawFunding` (NutzConverter.sol:L530, L542, L547-L551).

**Paths walked:**
- `notifyEpochFunding` → transfer succeeds (state + tokens) ✓ / transfer reverts (both undone) ✓ / `amounts[i] == 0` (no call, no state) ✓.
- `notifyDrawFunding` → same three outcomes ✓.
- `postRoot` → cap at L293 on all five tokens before any write ✓; skip loop before the cap so `carryIn` includes skipped funding ✓ (`carryIn` snapshot at L289 is taken after the loop at L284-L286).
- `voidRoot` → restores carry exactly (argument above); checked arithmetic: `carry + totals ≥ funded` because `carry = funded + carry_prev − totals` at that moment. ✓
- `claim` / `claimMany` / `pushClaims` → `_settle` per leaf (bounded), then `_payout` of exactly the settled sums; the push fee is carved out of, not added to, the holder's settled USDG ✓; keeper paid via the same `_payout` (stuck if the keeper's address is refused) ✓.
- `claimStuck` → sends the recorded amount only ✓.
- `pullAcorn` → sends the pool only ✓.
- Any other outflow → none (search below).

**Searched:**
- Token-moving calls in `NutzDistributor.sol` (`safeTransfer|transfer(|.call(|approve|selfdestruct|delegatecall`) → L215, L218, L246 (`safeTransferFrom` in, behind `funded +=`); L233 (`safeTransfer` out, pool); L438 (`safeTransfer` out, stuck); L486 (`call(transfer)` out, `_payout`). No `approve`, no `delegatecall`, no `selfdestruct`, no arbitrary `call` target (L486's target is `tokens(i)`, an immutable).
- `funded[` writes → L210, L242 only. `claimed[i]` writes → L460 only. `carry[i]` writes → L294, L316, L332 only. `stuckOf` writes → L436, L474 only. `acornPoolUsdg` writes → L212, L231 only.
- `unchecked` in `NutzDistributor.sol` → 0 hits; all arithmetic on these paths is checked.
- Fee-on-transfer / rebasing assumptions: the invariant needs `safeTransferFrom(amount)` to deliver `amount`. §2.5 states "no fee-on-transfer; not rebasing" for the Stock Tokens and USDG is "Standard ERC-20"; nothing in `src/` measures balance deltas on funding. Recorded as the one assumption the construction rests on.

**How the verdict was reached:** `implemented`: every inflow increments `funded` in the same transaction that pulls the tokens with a reverting transfer; every outflow is either bounded by `claimed` (which is bounded by `totals`, which is bounded by `funded + carry`, whose accounting was walked through post, skip and void) or comes out of a pool the invariant does not count; and no other outflow exists. Not `stronger-than-spec`: the extra slack (`stuck`, `acornPoolUsdg`) is what the spec's `stuck` and Acorn design describe, not an undocumented constraint.

**Open questions:**
- `_tryTransfer` L485-L488 treats an empty return with `ok == true` as success without an `extcodesize` check (OZ's `_callOptionalReturnBool` L208 adds one). A reward token with no code would count as paid (`claimed` up, balance unchanged); the invariant still holds (the left side does not fall), the holder is the loser. The five tokens are BeaconProxies (§2.5) and always have code; noted for completeness, not as a divergence.
- If a Stock Token ever charged a transfer fee (contrary to §2.5), `funded` would exceed what arrived and the invariant would break silently on the next full claim; nothing on-chain would detect it.
