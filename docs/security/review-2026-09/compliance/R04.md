## R04 — Push fee capped at 5% of the wallet's USDG regardless of inputs; rate has a contract-side sanity range

> "Bound: `MAX_PUSH_FEE_BPS` caps the deduction at 5% of a wallet's USDG regardless of inputs, and the rate has a contract-side sanity range."
> — docs/spec/engineering-spec.md §6, "Threat: keeper key compromise" (L271)

Supporting text, same document:

> "`fee = (PUSH_GAS_BASE + leaves × PUSH_GAS_PER_LEAF) × gasPriceWei × usdgPerEth / 1e18`, refused if `fee > pushedUsdg × 500 / 10000` (the wallet keeps accumulating). Stocks in full, USDG minus fee to the holder, the batch's total fee in one transfer to `msg.sender` (the gas payer). `usdgPerEth` must lie in `[min, max]` set by `setRateRange` (2-of-3, no oracle in the money path)."
> — §3.3 (L168)

**Verdict:** implemented · confidence: high

**What this demands of an implementation:** in `pushClaims`, whatever `gasPriceWei` and `usdgPerEth` the Keeper passes, the USDG deducted from a holder must never exceed 5% of the USDG being pushed for that holder, with the refusal (not a clamp) semantics §3.3 states; and `usdgPerEth` must be checked against a minimum and maximum stored in the contract and settable only by the Signers.

**Where enforcement lives:**

```solidity
// src/NutzDistributor.sol:L44
    uint256 public constant MAX_PUSH_FEE_BPS = 500;
// src/NutzDistributor.sol:L389-L391   rate range
        if (usdgPerEth < minUsdgPerEth || usdgPerEth > maxUsdgPerEth) {
            revert RateOutOfRange(usdgPerEth);
        }
// src/NutzDistributor.sol:L404-L407   fee and cap, per entry
            uint256 fee = (PUSH_GAS_BASE + pe.ids.length * PUSH_GAS_PER_LEAF) * gasPriceWei * usdgPerEth / 1e18;
            if (fee > sum[USDG] * MAX_PUSH_FEE_BPS / 10_000) revert PushFeeTooHigh(pe.account);
            sum[USDG] -= fee;
            totalFee += fee;
```
- L405: `fee` is compared to `floor(sum[USDG] × 5%)`, where `sum[USDG]` (L397-402) is the USDG of every leaf settled for this entry's account. Exceeding reverts the batch; nothing is clamped, so a fee that passes is at most 5%.
- L404 is checked arithmetic (0.8.37): an overflow from absurd `gasPriceWei` reverts rather than wrapping to a small fee.
- Only USDG is reduced (L406); stocks are paid in full.
- Range: constructor L179 rejects `minRate_ == 0 || minRate_ > maxRate_` and stores L184-185; `setRateRange` L423-429 repeats the check and is 2-of-3 (`_require2of3`, Signers.sol L121-129). `minUsdgPerEth`/`maxUsdgPerEth` are written nowhere else.

**Paths walked:**
- `pushClaims` with any `usdgPerEth` outside `[min, max]` → L389 revert before any settle. ✓
- Any entry whose fee exceeds 5% → L405 revert, whole batch. ✓
- Entry with `sum[USDG] == 0` (stock-only allocation): cap is 0, so any positive fee reverts; fee 0 (when `gasPriceWei == 0` or both gas immutables are 0) passes with no deduction. ✓
- The same account split across several entries in one batch (different `ids` each; the per-account flag is per id, L451): each entry's fee ≤ 5% of that entry's USDG, so the sum of deductions ≤ 5% of the total USDG pushed for the account. The "wallet's USDG" bound survives splitting. ✓
- `gasPriceWei` itself is not compared to `tx.gasprice` or bounded; the document does not ask for that ("overstate gas price […] Bound: `MAX_PUSH_FEE_BPS`"), the 5% cap is the stated bound. ✓
- The fee is paid via `_payout(msg.sender, feeOnly)` L414-418, so it is subject to R03's arrival-or-stuck.

**Searched:**
- `MAX_PUSH_FEE_BPS` in src/ → L44 declaration, L405 use. Nowhere else (no second fee path).
- `minUsdgPerEth|maxUsdgPerEth` in src/ → L98-99 declarations, L184-185 constructor, L389 check, L426-427 setter; and the Converter reads `DISTRIBUTOR.minUsdgPerEth()` at NutzConverter.sol L450 (the ETH→USDG floor, a different use, not this record's).
- `sum[USDG] -=` / other USDG deductions → L406 only.
- `usdgPerEth` → L384 param, L389-390 check, L404 formula. No use before the check.

**How the verdict was reached:** the cap is a strict comparison against the settled USDG on the only fee path, with revert semantics matching §3.3, and the rate check precedes everything. Not `stronger-than-spec`: the document itself specifies the refusal semantics, the per-entry summing and the Signer-set range.
