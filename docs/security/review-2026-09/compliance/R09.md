## R09 — Two Venues, per-swap exact approval, own `minOut`, try/catch per Leg

> "Swaps go through SwapRouter02 (v3, primary) or directly against the v4 `PoolManager` singleton (secondary), each Leg under a per-swap exact approval and its own `minOut`; try/catch per leg."
> — docs/spec/engineering-spec.md §6, "Threat: router/token behavior"

> "Approvals are per-swap, exact amount, and zeroed after, even when the swap failed."
> — docs/spec/engineering-spec.md §2.3

> "4. ETH→USDG in one swap of `ethIn − opsAmt` through `routes[1]`. Not isolated: a Venue failure re-raises the Venue's own revert data"
> — docs/spec/engineering-spec.md §2.2 step 4

**Verdict:** implemented · confidence: high (v3 `minOut` delegated to the Venue: see Open questions)

**What this demands of an implementation:** (1) a Route's `venue` is accepted only if it is the v3 router or the v4 pool manager; (2) on any path that spends an ERC-20, the allowance granted to the Venue equals the Leg's `amountIn`, is granted immediately before the swap, and is returned to zero afterwards on both the success and the failure branch; (3) each Leg's own `Route.minOut` bounds that Leg's output on both Venues; (4) every Leg except ETH→USDG is wrapped so that a Venue revert is caught and the Leg skipped, while ETH→USDG re-raises.

**Where enforcement lives:**

- (1) `V3_ROUTER` and `V4_POOL_MANAGER` are immutables (L131-L132) set once in the constructor (L230-L231). Any other `venue` reverts the whole call — a Keeper bug per §2.1, not a market condition.
- (2) v3, ERC-20 input: `forceApprove(router, amountIn)` at L612 and `forceApprove(router, 0)` at L619. L619 is outside the `try`/`catch` and runs on both branches. `forceApprove` (OZ SafeERC20 L106-L111) sets the allowance to the exact value, resetting to zero first for tokens that require it. v3, ETH input: no allowance; `msg.value == amountIn` (L613). v4: no allowance at all; the input is paid inside the callback by a direct `safeTransfer` of exactly `order.amountIn` (L690) or `settle{value: order.amountIn}` (L688). Nothing is left approved on any path.
- (3) v3: `route.minOut` becomes `amountOutMinimum` (L609). v4: `route.minOut` is carried in the order (L643) and compared by the Converter itself at L676; `PartialFill` at L675 additionally rejects an under-filled input so no input can strand in the manager.
- (4) v3: `try … catch (bytes memory err)` at L613-L618 returns `ok=false, reason=err`. v4: `try V4_POOL_MANAGER.unlock` at L644-L649 catches everything raised inside the manager, hooks and the callback's own `PartialFill`/`InsufficientOutput`. Callers: `_sellNutz` L420-L422 (skip + `LegSkipped(0, reason)`), `_buyStock` L488-L489 (skip + `LegSkipped(leg, reason)`); `_ethToUsdg` uses `_runLegStrict` L575-L584, which re-raises `reason` verbatim (L579-L581). The disabled path in `_buyStock` (L483-L486) never touches the Venue.

**Paths walked:**
- v3, ERC-20 in, success: approve L612 → swap → zero L619 → return `ok`. ✓
- v3, ERC-20 in, Venue reverts: approve L612 → catch L616 → zero L619 → `ok=false`. ✓ (approval zeroed on failure)
- v3, ETH in (Legs `EthToUsdg`): no approval; value = `amountIn`; catch as above. ✓
- v3, NUTZ→ETH, success: output arrives as WETH; `withdraw` at L620 unwraps to native. This unwrap sits *outside* the try/catch: a revert in `WETH.withdraw` reverts the Sweep rather than skipping the Leg. `WETH` is the router's own WETH9 (constructor check L225-L226); `withdraw` pays the caller with a plain transfer into the Converter's empty `receive()` (L240). ✗ only under a WETH9 that refuses to unwrap what it just paid; recorded, not a divergence in normal operation.
- v3, `amountIn == 0`: early return L603-L606 without approval or Venue call. ✓
- v4, success: `unlock` → `unlockCallback` (only when `msg.sender == V4_POOL_MANAGER`, L657) → swap → deltas → checks L675-L676 → pay exactly `amountIn` → `take` output. The manager's `unlock` (lib/v4-core/src/PoolManager.sol L103-L113) reverts `CurrencyNotSettled` if any delta is left, so a short payment cannot succeed. ✓
- v4, any revert inside (hook, pool, callback checks): caught at L647. Since the callback reverted, the manager's transient state is rolled back with it; nothing left the Converter. ✓
- v4, `amountIn == 0`: early return L638-L641. ✓
- Route validation (`BadPath` L595-L600, `BadPoolKey` L631-L635, `NutzNotBound` L702): runs before any approval, so a bad Route reverts with nothing approved. ✓
- Distributor funding approvals (`_approveFunding` L504-L509): exact `amounts[i]` / `usdg`, granted at L495/L548 and zeroed at L497/L550 around `notifyEpochFunding` / `notifyDrawFunding`. These are not Venue swaps but follow the same rule; a revert inside the Distributor reverts the whole call, so no "zero on failure" branch is needed. ✓

**How the verdict was reached:** all four properties are present and were read, not inferred from names. The one wording mismatch is that the v4 path uses no approval at all (a direct exact transfer inside the callback) whereas the document says "each Leg under a per-swap exact approval"; the property the sentence protects — exactly `amountIn` leaves and no allowance survives the call — holds on v4 by construction, so this is documentation drift rather than `partial`. The unwrap outside the try/catch is a narrow path that requires WETH9 to misbehave; it does not change the verdict but belongs in the record.

**Open questions:**
- v3 `minOut` is enforced by the router (`amountOutMinimum`), not re-checked by the Converter after `exactInput` returns. Whether the deployed `0xCaf6…5cb2` enforces it cannot be established from this repository; §2.3's "the contract enforces `minOut` on every Leg" is literally true only on v4. A one-line post-check (`out < route.minOut` → treat as failure) would make the Converter's guarantee Venue-independent.
- §2.2 step 6 / §2.3 describe approvals as the mechanism on every Leg; on v4 there is none. Document fix.
